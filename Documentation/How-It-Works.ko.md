# VirtualAP의 동작 방식

[English](How-It-Works.md) | [简体中文](How-It-Works.zh-CN.md) | [繁體中文](How-It-Works.zh-TW.md) | [Русский](How-It-Works.ru.md) | [Français](How-It-Works.fr.md) | [Deutsch](How-It-Works.de.md) | [日本語](How-It-Works.ja.md) | [한국어](How-It-Works.ko.md)

VirtualAP는 휴대폰의 Wi-Fi 칩에 가상 AP 인터페이스 `ap0`를 만들고, 그 위에서 `hostapd`를 실행한 뒤, 두 모드 중 하나로 동작합니다. 아래의 모든 것은 `src/`에서 빌드한, root로 실행되는 정적 C 바이너리 `virtualap`이 합니다. 앱은 그 명령(`start`, `stop`, `status`, `clients`, `interfaces`, `caps`)만 호출합니다. 커널과는 netlink(링크, 주소, 라우트, 규칙에는 rtnetlink, 무선에는 nl80211)와 raw `ip_tables` 소켓을 통해 직접 대화합니다. `hostapd`와 `dnsmasq`를 실행하고, TTL 보정에만 `iptables`를, 관리 모드에서는 컨테이너를 찾아 그 안에서 OpenWrt 설정을 실행하기 위해 `droidspaces`를 실행합니다. 어떤 컨테이너가 실행 중인지, 관리 모드에서 앱이 제시하는 목록은 앱이 Droidspaces 자체에 묻습니다(`droidspaces show --json`, 또는 `--json` 이전 릴리스에서는 `show --format`).

## 라우팅 모드 (앱에서는 "인터페이스")

VirtualAP는 핫스팟의 네트워크 계층 전체를 소유합니다. `ap0`에 게이트웨이 주소(다른 것을 고르지 않았다면 `192.168.42.1/24`)를 주고, 자체 `dnsmasq`로 DHCP와 DNS를 제공하며(`.10`에서 `.50`까지 12시간 임대, DNS는 입력한 서버로, 기본값은 `1.1.1.1`과 `8.8.8.8`로 전달), 클라이언트를 업스트림을 통해 NAT합니다.

트래픽은 Android 자체 규칙보다 위에 고정한 정책 라우팅 규칙으로 유도합니다. Android의 규칙은 우선순위 10000에서 시작하므로 VPN의 포괄 규칙이 핫스팟의 트래픽을 가져갈 수 없습니다.

```
client -> ap0
       -> ip rule pref 7010: from all iif ap0 lookup <upstream table>
       -> MASQUERADE (-s <subnet> ! -d <subnet>)
       -> internet or VPN tunnel

reply  -> ip rule pref 7000: to <subnet> lookup main -> ap0
```

자동에서 업스트림은 인터페이스가 올라와 있는 다음 중 첫 번째입니다. Android netd의 기본 네트워크 규칙, 즉 지금 인터넷이 있는 네트워크로, 커널의 규칙 목록에서 읽고 Android 15가 적는 형태(모든 uid에 대한 uid 범위)도 포함합니다. 그것을 채우는 ROM을 위한 main 표의 기본 라우트입니다. 알려진 업링크 이름(`wlan*`, `eth*`, `v4-*`, `rmnet*`, `*ccmni*`)의 스캔은 IPv4만 봅니다. 항상 떠 있는 IMS 베어러가 IPv6에서 그것들과 일치하기 때문입니다. IPv6를 시도하기 전에 IPv4가 세 가지를 모두 거칩니다. 핫스팟, 테더, VPN 인터페이스는 자동에서 절대 고르지 않습니다. `-o`는 그 모든 것을 끄고 대신 우선순위 순서의 쉼표 구분 목록을 받으며, 제외는 없습니다. 올라와 있고 라우트가 있는 첫 항목이 이기고, 목록 전체에서 IPv4 라우트를 IPv6보다 먼저 봅니다. 라우트는 /8보다 넓을 때만 인정되므로 기본 라우트나 스플릿 터널 VPN의 `0.0.0.0/5`는 되고, 인터페이스 자신의 서브넷은 되지 않습니다.

앱의 드롭다운이 보여 주는 `interfaces`는 `-o`가 받아들일 것을 나열합니다. 어느 표에서든, 어느 주소 체계든 그런 라우트가 있는 링크이므로 IMS 베어러도 나타납니다. VirtualAP, Droidspaces, USB Arsenal이 만드는 것과 netd의 `dummy0`은 빠집니다.

업스트림이 없는 것은 오류가 아니라 정상 상태입니다. AP는 규칙 7000만으로 올라오고, 클라이언트는 즉시 거부되며, 모니터는 업스트림이 나타나면 규칙 7010을 추가합니다. 방화벽 규칙은 Android의 xtables 잠금 아래 raw `ip_tables` 소켓으로 들어갑니다. netd와 `iptables -w`가 잡는 것과 같은 잠금이므로 어느 쪽도 상대의 변경을 덮어쓰지 않습니다.

AP 서브넷의 라우트는 Android의 `local_network` 표(97)에도 복제됩니다. 그것이 없으면 Droidspaces 컨테이너(출발지 `172.28.0.0/16`)에서 핫스팟 클라이언트로 가는 응답이 WAN 표로 흘러 `ap0`가 아니라 물리 업링크로 나가게 되어, 클라이언트가 컨테이너 안의 서비스에 닿을 수 없습니다.

### IPv6

클라이언트는 업스트림에 전역 주소가 있을 때만 IPv6를 받습니다. ULA만 내주는 Wi-Fi 네트워크에서는 AP가 IPv4 전용으로 남습니다. 주는 방법은 두 가지이고, 이 순서로 시도합니다.

- NAT66, Droidspaces의 방식은 커널에 MASQUERADE가 있는 `ip6table_nat`이 있고 업스트림의 표에 IPv6 기본 라우트가 있을 때 씁니다. `ap0`는 IPv4 서브넷을 따라 번호를 매긴 사설 /64(`192.168.42.1`의 경우 `fd76:6170:42::/64`)에서 `::1`을 갖고, `dnsmasq`는 자신을 DNS 서버로 삼아 그것을 광고하며, 클라이언트는 업스트림 밖으로 masquerade됩니다. 업스트림이나 프리픽스가 바뀌어도 손대지 않고 유지됩니다.
- 업스트림 자체의 /64는 Android 테더링이 하는 방식으로, IPv6 NAT가 없는 커널(기본 GKI에는 없습니다)에서 업스트림이 전역 /64를 가질 때 씁니다. `ap0`는 그 안의 EUI-64 주소를 갖고 `dnsmasq`는 프리픽스를 off-link로 광고하므로, 클라이언트는 모든 것을 게이트웨이로 보냅니다. 각 클라이언트 주소는 /128로 `ap0`에 라우팅되고 업스트림에서 NDP 프록시 항목으로 응답됩니다. 모니터는 3초마다 `ap0`에서 `ff02::1`로 핑을 보내 주소를 찾고, 그것이 주소를 드러내는 유일한 방법입니다. 모니터는 자기 에코에 대한 응답만 받아들이고, 휴대폰 자신의 주소나 업스트림의 이웃에 대한 응답은 절대 받지 않습니다. 규칙 7001은 어떤 클라이언트도 갖지 않은 /64 안의 주소로 가는 업스트림 패킷을 블랙홀 처리하며, 셀룰러에서는 그런 패킷이 홉 제한이 다할 때까지 튕겨 다닐 것입니다. 모니터가 없으면 프리픽스는 광고되지 않습니다.

둘 다 규칙 7002를 추가하며, 이 규칙은 클라이언트의 링크 로컬 주소로 가는 휴대폰 자신의 패킷에 라우트를 줍니다. Android는 인터페이스 자신의 라우트를 어떤 규칙도 읽지 않는 표에 넣고, 라우터 요청에 대한 `dnsmasq`의 응답이 그런 패킷 중 하나입니다. IPv6는 최선 노력입니다. 어떤 단계가 실패하면 AP는 IPv4 전용으로 남습니다.

## 모니터

성공한 시작은 `virtualap`을 모니터(`run/monitor.pid`)로 실행한 채 남깁니다. 스레드가 없는 프로세스 하나이며, Droidspaces의 라우트 모니터와 USB-Arsenal의 테더 데몬 뒤를 잇습니다. 커널의 링크, 주소, 라우트, 규칙 이벤트를 듣고, 한 무리의 마지막 이벤트 뒤 200ms에 한 번 보며, 그와 무관하게 3초마다 봅니다. netd가 이벤트 없이 `iptables`를 다시 쓰기 때문입니다. 각 확인은 다음을 합니다.

- 업스트림을 다시 해석하고 규칙 7010과 `run.state`를 새 업스트림으로 옮기므로, Wi-Fi에서 모바일로 넘어가는 인계가 클라이언트를 인터넷 없이 두지 않으며, 네트워크 없이 시작한 경우도 같은 방식으로 첫 업스트림을 얻습니다. 아무것도 찾지 못하면 자동은 규칙을 그대로 둡니다. 더 나은 곳이 없기 때문입니다. `-o`는 목록의 인터페이스가 돌아올 때까지 규칙을 제거하므로 그 트래픽이 다른 무엇으로도 나가지 않습니다.
- netd가 지운 규칙이나 방화벽 항목, 그리고 `ip_forward`를 되돌려 놓으며, 없을 때만 합니다. 그래서 자기 쓰기가 자기를 다시 깨우지 않습니다.
- 업스트림의 IPv6가 바뀌었을 때, 즉 새 프리픽스, 다른 인터페이스, IPv6의 등장이나 소실일 때 IPv6와 `dnsmasq`의 광고, 그리고 그에 따른 TTL 보정을 다시 합니다.

관리 모드에서는 대신 veth를 지켜보고, 컨테이너가 재시작하면 새 veth를 컨테이너에 꽂습니다. AP가 사라지면 종료하며, `stop`은 다른 무엇보다 먼저 그것을 죽입니다.

## 관리 모드 (`-K <container>`)

핫스팟의 LAN이 실행 중인 Droidspaces 컨테이너에 넘겨집니다. VirtualAP는 `ap0`에 주소를 주지 않고, `dnsmasq`를 실행하지 않으며, NAT를 설치하지 않습니다. 계층 2 경로를 만들고 컨테이너가 라우터가 됩니다.

```
client -> ap0 (bridge port, no address)
       -> vap-br0 -> vaplan0 (inside the container)
       -> container LAN (DHCP, DNS, firewall)
       -> container NAT -> container WAN -> internet
```

`ap0`는 호스트 브리지 `vap-br0`에 종속되고, 그 브리지는 주소를 나르지 않으며 IPv6가 꺼져 있어 컨테이너의 광고로 스스로를 구성하지 않습니다. veth 쌍이 호스트 쪽에서 브리지에 합류하고, 다른 쪽 끝은 컨테이너의 네트워크 네임스페이스 안에서 이미 `vaplan0`이라는 이름과 MAC을 가진 채 하나의 요청으로 만들어집니다. 호스트에서 만들어 옮긴 뒤 이름을 바꾸는 링크는 5.x 이전 커널에서 처음에 옛 이름으로 나타나고, OpenWrt의 netifd는 그것을 다시 보지 않습니다. 컨테이너가 OpenWrt이면 VirtualAP는 `droidspaces run`으로 실행하는 `uci` 스크립트 하나로 프로비저닝합니다. 설정된 게이트웨이 위의 정적 `vaplan` 인터페이스, netifd가 번호를 바꾸지 못하도록 IPv4 서브넷의 번호에 고정한 라우터 ULA의 IPv6 /64, 라우터 광고가 있는 DHCP 풀, 그리고 iptables 방화벽의 reload, 이미지에 방화벽 패키지가 없으면 MASQUERADE 규칙입니다. 다른 컨테이너는 `vaplan0`를 받아 스스로 구성합니다.

veth 쌍은 MTU 1508로 동작하고 `ap0`와 클라이언트는 1500에 머뭅니다. 삼성의 Broadcom 펌웨어는 받은 프레임의 약 4분의 1을 8바이트 CCMP MIC가 끝에 붙은 채로 올려보내고, 브리지나 veth는 MTU보다 18바이트 긴 프레임을 조용히 버립니다. 그래서 1500에서는 클라이언트의 최대 크기 프레임이 네 번에 한 번 잃어버려 컨테이너로의 업로드가 약 1 MB/s로 기어다녔습니다. 컨테이너 안의 IP 스택이 MIC를 잘라내고, `ra_mtu`로 RA가 클라이언트의 IPv6 MTU를 1500에 고정합니다. 그렇지 않으면 odhcpd가 포트의 1508을 광고하기 때문입니다.

veth의 양쪽 끝은 CPU0을 뺀 모든 CPU에 RPS를 받습니다. veth는 각 패킷을 보낸 CPU에 큐잉하고, 하나의 흐름이 여러 CPU에서 도착합니다. Wi-Fi 드라이버가 수신 작업을 코어에 나누고, TCP는 마지막 ACK를 받은 코어에서 보내기 때문입니다. RPS가 없으면 반대쪽 끝은 흐름을 순서 없이 보고, TCP는 결코 잃지 않은 데이터를 재전송합니다. `vaplan0`의 마스크는 컨테이너의 네트워크 네임스페이스로 들어가 그곳에 자체 `/sys`를 마운트하는 자식이 씁니다. 컨테이너가 고르는 심볼릭 링크를 따라 `/proc/<pid>/root`를 거치지 않습니다. 커널은 마스크를 쓸 때 온라인인 CPU만 유지하므로, 그 순간 주차된 코어는 AP가 재시작할 때까지 빠져 있습니다.

새 veth는 시작할 때마다 새 임의 MAC을 갖고, Windows는 네트워크 프로필을 게이트웨이의 MAC으로 식별하므로 앱이 하나를 고정할 수 있습니다. 시작 사이에 유지되는 임의 MAC이나 휴대폰 자신의 Wi-Fi MAC입니다. 컨테이너가 재시작하면 모니터가 새 veth를 꽂고, 재시작을 견뎌 낸 OpenWrt 설정이 그것을 받아들입니다. 옛 네임스페이스는 보통 veth를 함께 가져가지만, 무언가 참조를 잡고 있는 동안에는 마지막 프로세스보다 오래 살고, 그러면 호스트 쪽 끝이 아무것도 없는 곳을 바라본 채 남습니다. 그래서 모니터는 둘 다 확인합니다. 호스트 쪽 끝이 있고, 시작이 꽂은 프로세스가 꽂았던 네임스페이스에 아직 있습니다.

## TTL 보정

`-T 1`을 주면 포워딩된 패킷이 TTL 64(IPv6는 홉 제한 64)로 나가므로, 통신사에는 휴대폰 자신의 것처럼 보입니다. 규칙은 자체 mangle 체인 `vap_ttl`에 있고, `FORWARD`에서 클라이언트의 출발지 서브넷으로 일치합니다. `FORWARD`는 커널이 홉을 하나 줄인 뒤의 포워딩 패킷만 봅니다. 백엔드는 아무도 점프하지 않는 체인에 실제 규칙을 넣어 커널의 TTL 타깃(`CONFIG_NETFILTER_XT_TARGET_HL`)을 탐색하고, 탐색이 실패하면 앱이 그 옵션을 회색으로 표시합니다. 이것들이 아직 `iptables` 바이너리로 쓰는 유일한 규칙입니다.

## 무선

대부분의 휴대폰 칩은 스테이션이 연결된 채널에서만 비콘을 보낼 수 있으므로, 백엔드는 그 채널이 대역에 맞을 때 스테이션의 채널을 따릅니다. 스테이션의 채널은 스캔 결과에서 연결된 BSS의 주파수에서 오며, 그것이 `iw dev wlan0 link`가 읽는 값입니다. 삼성의 Broadcom 드라이버가 인터페이스 정보에서 채널을 생략하기 때문입니다. DFS 채널(52에서 144)의 스테이션은 2.4 GHz로 대체됩니다. 휴대폰 칩은 그곳에서 비콘을 보낼 수 없습니다. 다른 대역, 6 GHz 포함, 의 스테이션은 AP에게 자체 기본값을 남깁니다. 스테이션이 없으면 5 GHz는 채널 36에서, 2.4 GHz는 채널 6에서 시작합니다.

삼성의 Broadcom FullMAC 펌웨어는 세계 규제 도메인 "99"로 부팅하고, 프레임워크가 실제 국가를 밀어 넣지 않는 경우가 있어 모든 5 GHz 채널이 NO-IR로 남고 `hostapd`가 생존 확인 뒤 약 5초 만에 죽습니다. wiphy가 자체 관리형이라 `iw reg set`과 `hostapd`의 `country_code`가 무시됩니다. 유일한 지렛대는 서플리컨트의 제어 소켓을 통한 드라이버의 사설 `COUNTRY` 명령이고, 프레임워크가 보고하는 국가(`ensure_5g_ir`)로 보냅니다. phy가 그 채널을 NO-IR로 보고할 때만 작동하고, 그 뒤에도 채널이 여전히 NO-IR이면 AP는 2.4 GHz로 대체됩니다. `hostapd.conf`는 `country_code=US`를 유지합니다.

폭은 그 대역의 능력에서 오는, 칩과 채널이 할 수 있는 것을 따릅니다. 2.4 GHz의 40 MHz는 이름을 대고 요청할 때만이고, 5 GHz는 대역이 VHT를 나열하고 채널이 80 MHz 블록에 있을 때 최대 80 MHz입니다. HT40과 VHT는 `hostapd`가 20/40 MHz 공존 스캔을 건너뛰어야 하는데, FullMAC 칩은 AP 인터페이스에서 그것을 실행할 수 없습니다. 그 일을 하는 `no_pri_sec_switch` 옵션은 우리 `hostapd` 포크의 패치이고, 빌드가 패치의 존재를 확인합니다. `hostapd`가 2.4 GHz의 40 MHz를 거부하면 백엔드가 20으로 다시 시도합니다.

포크는 또한 `hostapd`에 드라이버가 MAC ACL을 가졌다고 결코 알리지 않고, 빌드가 그것도 확인합니다. 드라이버의 ACL은 목록보다 적은 주소를 담을 수 있고, 그 이상에서는 드라이버가 아무것도 갖지 못한 채 `hostapd`가 자체 검사를 건너뜁니다. 그래서 MAC 목록은 모든 칩에서 `hostapd`에서 검사됩니다. 목록에 있는 기기는 잠깐 연결되고 핸드셰이크 전에 제거됩니다. 삼성의 Broadcom 빌드는 ACL을 컴파일에서 빼 버렸고 gen4m에는 없으므로, 그들은 이미 이렇게 동작합니다. Qualcomm의 qcacld에는 있으므로 이 변경이 바꾸는 드라이버는 그것이고, 어떤 qcacld 휴대폰도 이것을 실행한 적이 없습니다.

MediaTek의 gen4m 드라이버에는 `dump_station`이 없으므로, 클라이언트 수는 제어 소켓을 통한 `hostapd` 자신의 스테이션 목록에서 옵니다. Android에는 `/tmp`가 없으므로 추상 주소에 바인딩하고, 멈춘 `hostapd`가 `status`를 붙잡지 못하도록 1초 타임아웃을 둡니다.

`clients`는 같은 목록을 걸으며 핸드셰이크를 마친 각 스테이션에 `mac ip name`을 출력하고, 모르는 것은 `-`로 출력합니다. `status`의 수는 같은 순회이므로 비밀번호가 틀린 기기는 둘 다에 없습니다. 앱은 연결된 기기 시트가 열려 있을 때만 묻습니다. 관리 모드는 `droidspaces`를 실행하고, 그 실행에는 5초 제한이 있습니다. libsu가 한 번에 명령 하나를 실행하기 때문입니다. 주소와 이름은 게이트웨이 /24에서 가장 최신 임대에서 옵니다. 라우팅 모드에서는 우리 `dnsmasq.leases`, 관리 모드에서는 컨테이너의 `/tmp/dhcp.leases`입니다. 후자는 `/proc/<pid>/root`를 통해 읽습니다. OpenWrt의 `/tmp`는 컨테이너의 마운트 네임스페이스에 있는 tmpfs이므로, 한 번에 한 구성 요소씩, tmpfs 위의 일반 파일일 때만 읽고, 컨테이너가 그곳에 남긴 심볼릭 링크나 FIFO, 바인드 마운트는 거부합니다. 호스트 이름을 보내지 않는 클라이언트나 그런 파일이 없는 컨테이너는 그 필드를 `-`로 남깁니다.

정적 주소의 기기는 가졌던 주소의 임대를 유지하므로 커널의 ARP 표가 그것을 바로잡습니다. 라우팅 모드에서는 `/proc/net/arp`, 관리 모드에서는 `/proc/<pid>/net/arp`이고, 관리 모드에서는 클라이언트의 LAN이 컨테이너에서 끝납니다. 임대는 표가 그것을 확인하거나 그 MAC에 다른 주소를 알지 못하는 동안 유지되고, 표는 임대가 없는 기기에도 주소를 줄 수 있습니다. 표는 무언가를 보낸 적 있는 기기만 가지고, 오래된 항목도 완료로 표시하므로, 기기가 방금 떠난 주소를 보여 줄 수 있습니다.

`block <mac> [name]`은 기기를 `/data/local/virtualap/blocklist`에 추가하고, `unblock <mac>`은 빼냅니다. `blocked`는 각각에 `mac name`을 출력하고, 이름이 없으면 `-`를 출력합니다. `allow`, `disallow`, `allowed`는 `allowlist`에 같은 일을 합니다. `allow-only on`은 허용 목록에 없는 모든 기기를 막고 연결된 기기도 끊으며, 목록이 비어 있으면 거부됩니다. 목록에서 마지막 기기가 빠지면 그것으로 꺼집니다. 그렇지 않으면 아무도 참여할 수 없기 때문입니다. 인수 없이 호출하면 `on`이나 `off`를 출력합니다. 그 상태는 목록 옆의 `allow_only` 파일입니다. 목록들과 마찬가지로 핫스팟이 켜져 있든 꺼져 있든 한 번에 명령 하나로 바뀌기 때문입니다. 기기는 한 목록에만 있고, 하나에 추가하면 다른 하나에서 빠집니다. `hostapd`가 허용 목록을 먼저 확인하므로 둘 다에 있는 기기를 들여보내기 때문입니다.

목록이 `ap.conf` 밖에 있는 것은 앱이 설정 한 번으로 넘기는 값이 아니라 항목 하나씩 편집하기 때문입니다. 파일은 `hostapd` 자체의 `deny_mac_file`과 `accept_mac_file`이고, 존재할 때만 그 설정에서 이름이 오릅니다. `hostapd`는 열 수 없는 목록에서는 시작하지 않기 때문입니다. 한 줄은 `mac #name`입니다. `hostapd`는 MAC 뒤의 것을 `atoi`로 VLAN id로 읽고, `#`이 그것을 0, 즉 VLAN 없음으로 만듭니다. 실행 중인 핫스팟은 제어 소켓으로 변경을 듣습니다. `DENY_ACL ADD_MAC`은 그 기기가 연결되어 있으면 끊고, 허용된 기기만 참여할 수 있게 되면 `ACCEPT_ACL DEL_MAC`도 그렇게 합니다. 시작은 파일을 먼저 다시 쓰고, `hostapd`가 읽을 수 있을지 확신할 수 없는 줄은 기록하며 버리며, 각 파일은 약 400개 기기를 담습니다.

앱은 기기 시트에서 확인 없이 차단합니다. 바로 옆에 차단 해제가 있기 때문입니다. 두 목록은 핫스팟이 꺼져 있을 때를 위해 설정에 유지합니다. 앱의 MAC 필드는 16진수 외에는 담지 못하고, 엔진이 거부하는 것을 거부합니다. 모두 0인 주소와 그룹 주소입니다. 어느 목록이든 그 MAC만 담습니다. 자기 MAC을 바꾸는 기기는 차단을 지나쳐 가고 허용 목록에서 빠지며, 휴대폰은 기본적으로 네트워크마다 임의 주소를 쓰므로, 입력할 것은 이 핫스팟에 대한 그 기기의 Wi-Fi 정보에 있는 주소입니다.

## 휴대폰에서

모든 것이 `/data/local/virtualap` 아래에 있습니다.

- `bin/`: `virtualap`, `hostapd`, `dnsmasq`. 휴대폰 아키텍처용 완전 정적 musl 바이너리입니다. `iptables`는 Android 자체의 것입니다.
- `ap.conf`: `KEY='value'` 줄로 된 핫스팟 설정. 앱은 화면의 내용이 유효하고 매 시작 전에 그것을 씁니다. 반쯤 채운 폼은 화면에 남습니다. 엔진은 읽기만 하고, 플래그가 그 실행에 한해 덮어씁니다. Wi-Fi 비밀번호가 들어 있으므로 root만 읽을 수 있습니다.
- `blocklist`, `allowlist`, `allow_only`: 차단된 기기와 허용된 기기, 그리고 그들만 참여할 수 있는지. 처음 쓰기 전에는 어느 것도 없습니다. 위의 [무선](#무선)을 보세요.
- `.boot_mode`: 핫스팟이 부팅 시 시작되면 `1`. 설정 토글이 쓰고 부팅 모듈이 읽습니다.
- `run.state`: 실행 중인 AP를 정리하는 데 필요한 것, 즉 게이트웨이, 업스트림, IPv6 모드와 인터페이스, 복구할 sysctl 값. `status`는 "running"을 그것과 `hostapd` pid 파일에서 판단하고, `stop`은 종료 전에 그것을 지웁니다.
- `run/`: pid 파일(`hostapd`, `dnsmasq`, 모니터), 생성된 `hostapd.conf`와 `dnsmasq.conf`, 임대, IPv6 클라이언트 목록, `hostapd`의 제어 소켓, 두 개의 시작이나 정지가 동시에 돌지 않게 하는 잠금.
- `logs/`: `ap.log`는 앱이 보여 준 모든 줄과 모니터가 한 일의 타임스탬프 사본이며 시작마다 잘립니다. 여기에 `hostapd.log`와 `dnsmasq.log`가 더해집니다. 그렇지 않으면 두 데몬이 실패 이유를 가지고 사라지기 때문입니다. 그리고 `boot-module.log`, 마지막 부팅에서 부팅 모듈이 한 일입니다.

pid 파일은 그 파일이 가리키는 프로세스가 기대한 프로그램을 실행 중일 때만 다뤄지므로, 재부팅 뒤 재사용된 pid에는 절대 시그널을 보내지 않습니다. 앱은 첫 실행 때와 APK가 다른 바이너리를 실을 때마다 `bin/`을 배포합니다. 빌드는 각 아키텍처 바이너리와 부팅 모듈의 해시인 `PAYLOAD_VERSION`을 그 옆에 쓰고, 앱은 그것을 마지막으로 배포한 것과 비교합니다.

백엔드를 배포하면 Droidspaces가 자기 것을 설치하는 것과 같은 방식으로 부팅 모듈인 `/data/adb/modules/virtualap`도 설치됩니다. root 관리자가 없는 휴대폰에는 그것이 없으므로, `.boot_mode`만 쓰는 설정 토글은 그것을 읽을 것이 없습니다. 모듈의 `service.sh`는 late start에서 실행되어 `sys.boot_completed`를 기다립니다. `.boot_mode`가 켜져 있으면 Wi-Fi 인터페이스가 나타나기를 25초 기다리고, 관리 모드에서는 컨테이너가 실행되기를 25초 더 기다리며, 둘 중 하나라도 아니면 시작을 건너뜁니다. 네트워크는 기다리지 않습니다. 핫스팟은 나중에 오는 업스트림을 따르기 때문입니다. 시작은 앱의 암호화된 저장소 밖에 있는 `ap.conf`를 읽으므로 부팅 시 시작에 잠금 해제가 필요 없습니다. 결과는 root 관리자에서 모듈의 설명으로 보입니다. 성공한 시작 뒤에는 앱이 실행될 수 없는 첫 잠금 해제를 기다렸다가 `HotspotBootReceiver`에 브로드캐스트를 보내고, 그것이 실행 중 알림을 띄웁니다.

## 빌드

`hostapd`와 `dnsmasq`는 `externals/` 아래의 git 서브모듈, 즉 우리 포크에서 `scripts/build-static.sh`가 빌드합니다. 각 아키텍처는 그 아키텍처의 Alpine 3.23 컨테이너에서, x86 호스트에서는 QEMU 아래에서 빌드되고, `-static -no-pie`를 써서 결과가 인터프리터 없는 독립 ELF가 됩니다. `dnsmasq` 포크는 `getpwnam("root")` 권한 강하를 뺍니다. Android의 `/etc/passwd`에는 root 항목이 없고 정적 musl은 그것을 합성하지 않기 때문입니다. `virtualap`은 libc 말고는 아무것도 링크하지 않고 컨테이너도 필요 없습니다. 루트 `Makefile`이 Droidspaces 방식으로 빌드하며, `~/toolchains/<triplet>-cross`(또는 `MUSL_CROSS`)의 musl-cross gcc로 `make aarch64 armhf`를 실행하고, `buildBackend` gradle 태스크가 매 앱 빌드 전에 그것을 돌립니다. 출력은 gitignore 대상인 `backend/<arch>/`에 놓이고, `prepareAssets` gradle 태스크가 세 바이너리를 APK의 assets로 모으며, 하나라도 없으면 실패합니다.

`src/`는 계층마다 폴더 하나이고, 각 폴더는 `src/include/<folder>/` 아래 공개 헤더 하나를 가지며, 파일들이 그 이상을 공유하면 소스 옆에 사설 `internal.h`를 둡니다: `core`, `cli`, `net`(rtnetlink, 그리고 `net/ipt/`의 `ip_tables` 엔진), `radio`(nl80211, 제어 소켓, 채널 정책), `mode`(라우팅, 관리, IPv6, `hostapd`와 `dnsmasq`), `monitor`, `cmd`. `make check`는 `tests/`의 검증을 실행하고, netlink 관련 검증은 버려지는 사용자 및 네트워크 네임스페이스 안에서 커널을 상대로 하므로 root도 휴대폰도 필요 없습니다. 휴대폰용으로 빌드해 그곳에서 root로 실행하면 실제 `ip_tables`까지 시험합니다.

CI는 각 아키텍처의 `hostapd`와 `dnsmasq`를 ARM 러너에서 빌드하고, `externals/`와 `scripts/` 트리에 캐시합니다. 그다음 APK 작업이 Droidspaces가 배포한 musl 툴체인을 가져오고(sha256으로 확인하며 릴리스 URL에 캐시), 경고를 오류로 삼아 `make check`와 `make aarch64 armhf`를 실행하고, JDK 17로 APK를 빌드합니다. `src/include/virtualap.h`의 `VAP_VERSION`과 일치하는 `v*` 태그를 푸시하면 APK, `SHA256SUMS` 파일, 이전 태그 이후의 모든 커밋으로 만든 체인지로그를 담은 릴리스를 게시합니다. 태그가 일치해야 하고 서명 키가 있어야 하며, 그렇지 않으면 실행이 멈춥니다. CI는 포매터도 린터도 실행하지 않습니다.

`make bump NEW=x.y.z`는 `VAP_VERSION`을 다시 쓰고, Makefile과 gradle, CI가 모두 그것을 거기서 읽습니다. APK의 versionCode는 릴리스 코드(major·10000 + minor·100 + patch) 곱하기 10000에 `git rev-list --count HEAD`를 더한 값이므로, 모든 커밋의 APK가 직전 것을 덮어 설치됩니다. 이 수에는 전체 이력이 필요하고, 그래서 APK 작업이 `fetch-depth: 0`으로 체크아웃합니다. 얕은 클론은 1을 세고, `.git`이 없는 트리는 0을 셉니다. 부팅 모듈의 `module.prop`은 릴리스 코드만 받습니다. 그것이 `PAYLOAD_VERSION`에 해시되기 때문입니다.

## 번역

앱의 텍스트는 `Android/app/src/main/res/values/strings.xml`에, 복수형은 그 옆의 `plurals.xml`에 있습니다. 두 Weblate 컴포넌트 `Strings`와 `Plurals`이고, Droidspaces와 같은 배치입니다. 둘 다 파일 형식 Android String Resource를 쓰고, 파일 마스크는 `Android/app/src/main/res/values-*/strings.xml` 또는 `plurals.xml`이며, `values/`의 기준 파일이 단일 언어 기준 언어 파일이자 새 번역의 템플릿이고, 언어 코드는 Android 방식(`values-pt-rBR`)입니다. Weblate의 Cleanup translation files 애드온을 켜세요. 기준 파일에서 지운 키가 번역에 남아 있으면 lint의 `ExtraTranslation`이 되고, 그것은 치명적이므로 릴리스 빌드가 그것이 사라질 때까지 실패합니다. 번역이 없는 것은 영어로 대체될 뿐입니다.

앱은 설정의 언어 선택기가 다르게 말할 때까지 시스템 언어를 따릅니다. 선택기의 목록과 Android 13의 앱별 언어 목록은 한 파일입니다. `generateLocaleConfig`가 `values-*` 폴더에서 `res/xml/_generated_res_locale_config.xml`을 쓰고, `res/resources.properties`가 `res/values`를 영어로 말하며, `LocaleHelper`가 그 결과를 읽습니다. 그래서 Weblate에서 병합된 언어는 번역이 얼마나 적든 다음 빌드에서 제시됩니다. 선택은 AppCompat을 거치고, `MainActivity`가 `AppCompatActivity`인 이유입니다. Android 13 이상은 그것을 시스템에 보관하고, 8에서 12에서는 AppCompat이 직접 저장하고 애플리케이션이나 서비스가 아니라 액티비티를 감쌉니다. 그래서 그곳에서는 알림과 빠른 설정 타일이 시스템 언어로 남습니다. 어느 버전에서든 이미 떠 있는 알림은 다음 업데이트 때 새 언어를 받습니다. 로그는 영어로 남습니다. 엔진이 출력한 것이기 때문입니다. 그 로그와 QR 시트의 비밀번호를 위한 JetBrains Mono가 유일하게 번들된 글꼴이고, 번역된 모든 레이블은 시스템 글꼴이라 어떤 문자 체계든 그려집니다.
