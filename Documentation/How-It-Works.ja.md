# VirtualAP の仕組み

[English](How-It-Works.md) | [简体中文](How-It-Works.zh-CN.md) | [繁體中文](How-It-Works.zh-TW.md) | [Русский](How-It-Works.ru.md) | [Français](How-It-Works.fr.md) | [Deutsch](How-It-Works.de.md) | [日本語](How-It-Works.ja.md) | [한국어](How-It-Works.ko.md)

VirtualAP はスマートフォンの Wi-Fi チップ上に仮想 AP インターフェース `ap0` を作成し、その上で `hostapd` を動かし、その後 2 つのモードのいずれかで動作します。以下のすべては、root として動作し `src/` からビルドされる静的 C バイナリ `virtualap` が行います。アプリはそのコマンド（`start`、`stop`、`status`、`clients`、`interfaces`、`caps`）を呼ぶだけです。カーネルとは netlink（リンク、アドレス、ルート、ルールには rtnetlink、無線には nl80211）と生の `ip_tables` ソケットを通じて直接対話します。起動するのは `hostapd` と `dnsmasq`、TTL 修正のためだけの `iptables`、そして管理モードではコンテナを見つけてその中で OpenWrt のセットアップを実行するための `droidspaces` です。どのコンテナが動作しているか、管理モードのためにアプリが提示する一覧は、アプリが Droidspaces 自身に問い合わせます（`droidspaces show --json`、`--json` より前のリリースでは `show --format`）。

## ルーティングモード（アプリでは「インターフェース」）

VirtualAP はホットスポットのネットワーク層全体を所有します。`ap0` にゲートウェイアドレス（別のものを選ばない限り `192.168.42.1/24`）を与え、独自の `dnsmasq` で DHCP と DNS を提供し（リースは `.10` から `.50` まで 12 時間、DNS は入力したサーバー、既定では `1.1.1.1` と `8.8.8.8` に転送）、クライアントを上流経由で NAT します。

通信は Android 自身のルールより上に固定したポリシールーティングルールで誘導します。Android のルールは優先度 10000 から始まるため、VPN のキャッチオールルールがホットスポットの通信を奪うことはありません：

```
client -> ap0
       -> ip rule pref 7010: from all iif ap0 lookup <upstream table>
       -> MASQUERADE (-s <subnet> ! -d <subnet>)
       -> internet or VPN tunnel

reply  -> ip rule pref 7000: to <subnet> lookup main -> ap0
```

自動では、上流はインターフェースが起動している次のうち最初のものです。Android の netd の既定ネットワークのルール、つまり今インターネットを持つネットワークで、カーネルのルール一覧から読み取り、Android 15 が書く形式（全 uid にわたる uid 範囲）も含みます。main テーブルの既定ルートは、それを設定する ROM 向けです。既知のアップリンク名（`wlan*`、`eth*`、`v4-*`、`rmnet*`、`*ccmni*`）の走査もありますが、IPv4 のみです。常時起動の IMS ベアラが IPv6 ではそれらに一致してしまうからです。IPv6 を試す前に、IPv4 がこの 3 つすべてを通ります。ホットスポット、テザリング、VPN のインターフェースは自動では決して選ばれません。`-o` はそれらすべてを無効にし、代わりに優先順のカンマ区切りリストを取り、除外はありません。起動していてルートを持つ最初の項目が勝ち、IPv6 より先にリスト全体の IPv4 ルートが対象になります。ルートが数えられるのは /8 より広い場合だけなので、既定ルートやスプリットトンネル VPN の `0.0.0.0/5` は該当し、インターフェース自身のサブネットは該当しません。

`interfaces` はアプリのドロップダウンに表示され、`-o` が受け入れるものを一覧します。つまり、いずれかのテーブルにそのようなルートを持つリンクで、どちらのアドレスファミリーでも対象なので、IMS ベアラも現れます。VirtualAP、Droidspaces、USB Arsenal が作成するものと netd の `dummy0` は除きます。

上流がないのはエラーではなく通常の状態です。AP はルール 7000 だけで立ち上がり、クライアントはすぐに拒否され、上流が現れるとモニターがルール 7010 を追加します。ファイアウォールのルールは、Android の xtables ロックの下で生の `ip_tables` ソケットを通じて入ります。netd と `iptables -w` が保持するのと同じロックなので、どちらの側も相手の変更を上書きすることはありません。

AP のサブネットのルートは、Android の `local_network` テーブル（97）にも複製されます。これがなければ、Droidspaces コンテナ（送信元 `172.28.0.0/16`）からホットスポットのクライアントへの応答が WAN テーブルへ落ち、`ap0` ではなく物理的なアップリンクから出てしまうため、クライアントはコンテナ内のサービスに到達できません。

### IPv6

クライアントが IPv6 を得るのは、上流がグローバルアドレスを持つ場合だけです。ULA だけを配る Wi-Fi ネットワークでは、AP は IPv4 のみのままです。与える方法は 2 つあり、この順で試します：

- NAT66 は Droidspaces の方式で、カーネルに MASQUERADE を伴う `ip6table_nat` があり、上流のテーブルに IPv6 の既定ルートがある場合に使います。`ap0` は IPv4 のサブネットに合わせた番号のプライベート /64（`192.168.42.1` なら `fd76:6170:42::/64`）で `::1` を取り、`dnsmasq` は自身を DNS サーバーとしてそれを広告し、クライアントは上流からマスカレードされて出ていきます。上流やプレフィックスが変わっても影響を受けません。
- 上流自身の /64 は Android のテザリングがやる方式で、IPv6 の NAT がないカーネル（素の GKI には入っていません）で、上流がグローバルな /64 を持つ場合に使います。`ap0` はその中の EUI-64 アドレスを取り、`dnsmasq` はプレフィックスをオフリンクとして広告するため、クライアントはすべてをゲートウェイへ送ります。各クライアントのアドレスは /128 として `ap0` へルートされ、上流では NDP プロキシのエントリーで応答されます。モニターは 3 秒ごとに `ap0` から `ff02::1` へ ping してアドレスを見つけます。これを明らかにできるのはそれだけです。受け入れるのは自分自身の echo への応答だけで、スマートフォン自身のアドレスや上流の近隣のアドレスに対するものは決して受け入れません。ルール 7001 は、どのクライアントも持たない /64 内のアドレスへの上流のパケットをブラックホール化します。そうしなければセルラーではホップリミットが尽きるまで跳ね返り続けます。モニターがなければプレフィックスは広告されません。

どちらもルール 7002 を追加し、スマートフォン自身のパケットがクライアントのリンクローカルアドレスへ向かうときにルートを与えます。Android はインターフェース自身のルートをどのルールも読まないテーブルに記録し、ルーター要請への `dnsmasq` の応答はそうしたパケットの 1 つです。IPv6 はベストエフォートです。あるステップが失敗すると、AP は IPv4 のみのままです。

## モニター

開始に成功すると、`virtualap` はモニター（`run/monitor.pid`）として動作し続けます。スレッドを持たない 1 つのプロセスで、Droidspaces のルートモニターや USB-Arsenal のテザリングデーモンの後を継ぐものです。カーネルのリンク、アドレス、ルート、ルールのイベントを待ち受け、バーストの最後のイベントから 200 ms 後に確認し、それとは別に 3 秒ごとにも確認します。netd がイベントなしで `iptables` を書き換えるからです。各確認では：

- 上流を再解決し、ルール 7010 と `run.state` を新しい上流へ移します。Wi-Fi からモバイルへの引き継ぎでクライアントがインターネットを失わないためであり、ネットワークなしで開始した場合も同じ方法で最初の上流を得ます。何も見つからない場合、自動ではルールをそのままにし、向ける先により良いものはありません。`-o` ではリストにあるインターフェースが戻るまでルールを削除するため、その通信が他の何かから出ていくことはありません；
- netd が消したルールやファイアウォールのエントリー、および `ip_forward` を、欠けているときだけ戻します。自身の書き込みで再び目覚めることがないようにするためです；
- 上流の IPv6 が変わったとき、つまり新しいプレフィックス、別のインターフェース、IPv6 の出現や消失のときに、IPv6、それに伴う `dnsmasq` の広告、TTL 修正をやり直します。

管理モードでは代わりに veth を監視し、コンテナが再起動したときに新しい veth をコンテナへ差し込みます。AP がなくなると終了し、`stop` は何よりも先にそれを終了させます。

## 管理モード（`-K <container>`）

ホットスポットの LAN は、動作中の Droidspaces コンテナに渡されます。VirtualAP は `ap0` にアドレスを与えず、`dnsmasq` も動かさず、NAT も設定しません。レイヤー 2 の経路を作り、ルーターはコンテナです。

```
client -> ap0 (bridge port, no address)
       -> vap-br0 -> vaplan0 (inside the container)
       -> container LAN (DHCP, DNS, firewall)
       -> container NAT -> container WAN -> internet
```

`ap0` はホスト側のブリッジ `vap-br0` に接続されます。このブリッジはアドレスを持たず、IPv6 が無効なので、コンテナの広告から自分自身を構成することはありません。veth ペアはホスト側でブリッジに参加し、もう一方の端はコンテナのネットワーク名前空間の内部に、すでに `vaplan0` という名前と MAC を持つものとして、1 つの要求で作成されます。ホスト側で作成して移動後に名前を変えたリンクは、5.x より前のカーネルでは最初に古い名前で現れ、OpenWrt の netifd はそれを再度見ることはありません。コンテナが OpenWrt のとき、VirtualAP は `droidspaces run` で実行する 1 つの `uci` スクリプトでそれをプロビジョニングします。設定されたゲートウェイ上の静的インターフェース `vaplan`、netifd が番号を振り直せないように IPv4 サブネットの番号に合わせてルーターの ULA から取った IPv6 /64、ルーター広告を伴う DHCP プール、そして iptables ファイアウォールの再読み込み、またはイメージにファイアウォールのパッケージがない場合の MASQUERADE ルールです。それ以外のコンテナは `vaplan0` を受け取り、自分で設定します。

veth ペアは MTU 1508 で動作し、`ap0` とクライアントは 1500 のままです。Samsung の Broadcom ファームウェアは、受信フレームのおよそ 4 分の 1 を、8 バイトの CCMP MIC を末尾に付けたまま渡してきます。ブリッジや veth は、自身の MTU に 18 バイトを加えた長さを超えるフレームを黙って解放するため、1500 ではクライアントからのフルサイズのフレームが 4 回に 1 回失われ、コンテナへのアップロードは約 1 MB/s まで落ちました。コンテナ内の IP スタックが MIC を取り除き、RA が `ra_mtu` でクライアントの IPv6 MTU を 1500 に固定します。そうしなければ odhcpd がポートの 1508 を広告するからです。

veth の両端に RPS を設定し、CPU0 を除くすべての CPU を対象にします。veth は各パケットをそれを送った CPU のキューに入れ、1 つのフローが複数の CPU から届きます。Wi-Fi ドライバが受信処理をコアに分散し、TCP は最後の ACK を受け取ったコアから送信するからです。RPS がないと、遠端はフローを順序外れに受け取り、TCP は失われていないデータを再送します。`vaplan0` のマスクは、コンテナのネットワーク名前空間に入り、そこで独自の `/sys` をマウントする子プロセスが書き込みます。コンテナが選ぶシンボリックリンクである `/proc/<pid>/root` を通すことは決してありません。カーネルはマスクを書き込む時点でオンラインの CPU だけを保持するため、その瞬間に停止していたコアは AP が再起動するまで対象外のままです。

新しい veth は起動のたびに新しいランダム MAC を持ち、Windows はゲートウェイの MAC でネットワークプロファイルを識別するため、アプリは MAC を固定できます。起動をまたいで保持されるランダム MAC、またはスマートフォン自身の Wi-Fi MAC です。コンテナが再起動すると、モニターは新しい veth を差し込み、再起動を生き延びた OpenWrt の設定がそれを拾います。古い名前空間は通常 veth を一緒に持っていきますが、何かが参照を保持している間は最後のプロセスより長く生き残り、そのときホスト側の端は何もない先に接続されたまま残ります。そこでモニターは両方を確認します。ホスト側の端が存在すること、そして開始時に差し込んだプロセスが、差し込んだ名前空間にまだいることです。

## TTL 修正

`-T 1` を指定すると、転送されるパケットは TTL 64（IPv6 ではホップリミット 64）で出ていくため、事業者からはスマートフォン自身のものに見えます。ルールは独自の mangle チェーン `vap_ttl` にあり、`FORWARD` でクライアントの送信元サブネットに一致させます。このチェーンが見るのは、カーネルがホップを 1 つ減らした後の転送パケットだけです。バックエンドは、どこからもジャンプされないチェーンに実際のルールを追加することで、カーネルが TTL ターゲット（`CONFIG_NETFILTER_XT_TARGET_HL`）を持つか調べます。アプリはこの調査が失敗するとオプションをグレーアウトします。`iptables` バイナリが今も書くルールはこれらだけです。

## 無線

ほとんどのスマートフォンのチップは、ステーションが接続しているチャンネルでしかビーコンを送れないため、バックエンドは帯域に合う場合にステーションのチャンネルに追従します。ステーションのチャンネルは、スキャン結果で関連付けられている BSS の周波数から取ります。これは `iw dev wlan0 link` が読むもので、Samsung の Broadcom ドライバがインターフェース情報からチャンネルを省略するためです。DFS チャンネル（52 から 144）のステーションでは 2.4 GHz にフォールバックします。スマートフォンのチップはそこでビーコンを送れないからです。別の帯域、6 GHz を含む、にいるステーションでは、AP は自身の既定値のままです。ステーションがない場合、5 GHz はチャンネル 36、2.4 GHz はチャンネル 6 で開始します。

Samsung の Broadcom FullMAC ファームウェアはワールド regdomain の「99」で起動し、フレームワークが実際の国を決して通知しないことがあるため、すべての 5 GHz チャンネルが NO-IR のままになり、`hostapd` は生存確認の後、約 5 秒で停止します。wiphy は自己管理なので `iw reg set` と `hostapd` の `country_code` は無視されます。唯一の手段は、サプリカントの制御ソケット経由でドライバのプライベートな `COUNTRY` コマンドを、フレームワークが報告する国とともに送ることです（`ensure_5g_ir`）。これが発火するのは phy がそのチャンネルを NO-IR と報告したときだけで、その後もチャンネルが NO-IR のままであれば AP は 2.4 GHz にフォールバックします。`hostapd.conf` は `country_code=US` を保持します。

幅はチップとチャンネルができること、つまりその帯域のケイパビリティに従います。2.4 GHz の 40 MHz は名前で要求されたときだけ、5 GHz は帯域が VHT を挙げていてチャンネルが 80 MHz のブロック内にあるとき最大 80 MHz です。HT40 と VHT には `hostapd` が 20/40 MHz の共存スキャンを飛ばす必要があり、FullMAC のチップは AP インターフェースでそれを実行できません。それを行う `no_pri_sec_switch` オプションは私たちの `hostapd` フォークのパッチであり、ビルドはそのパッチが存在することを検証します。`hostapd` が 2.4 GHz の 40 MHz を拒否した場合、バックエンドは 20 で再試行します。

このフォークはまた、ドライバが MAC ACL を持つことを `hostapd` に決して伝えず、ビルドはそれも検証します。ドライバの ACL はリストより少ないアドレスしか保持できないことがあり、それを超えると `hostapd` は自身のチェックを飛ばす一方でドライバは何も保持しません。そのため MAC のリストはすべてのチップで `hostapd` 内でチェックされます。リストにある端末は一瞬関連付けし、ハンドシェイクの前に削除されます。Samsung の Broadcom のビルドは ACL をコンパイル時に外しており、gen4m には ACL がないため、これらはすでにこのように動作します。Qualcomm の qcacld には ACL があるため、これが変わるのはそのドライバであり、qcacld のスマートフォンではまだ実行されていません。

MediaTek の gen4m ドライバには `dump_station` がないため、クライアント数は `hostapd` 自身のステーション一覧をその制御ソケット経由で取得します。Android には `/tmp` がないため抽象アドレスにバインドし、タイムアウトは 1 秒なので、`hostapd` がハングしても `status` が止まることはありません。

`clients` は同じ一覧をたどり、ハンドシェイクを終えた各ステーションについて `mac ip name` を出力し、分からないものは `-` を出力します。`status` の数も同じたどり方なので、パスワードを間違えた端末はどちらにも含まれません。アプリが問い合わせるのは接続中のデバイスシートが開いている間だけで、管理モードでは `droidspaces` を起動するためです。libsu は 1 度に 1 つのコマンドしか実行しないため、その起動には 5 秒の制限があります。アドレスと名前は、ゲートウェイの /24 の中で最も新しいリースから取ります。ルーティングモードでは私たち自身の `dnsmasq.leases`、管理モードではコンテナの `/tmp/dhcp.leases` です。後者は `/proc/<pid>/root` 経由で読みます。OpenWrt の `/tmp` はコンテナのマウント名前空間内の tmpfs だからです。1 度に 1 つのコンポーネントずつ読み、tmpfs 上の通常ファイルのみを対象とするため、コンテナがそこに残したシンボリックリンク、FIFO、バインドマウントは拒否されます。ホスト名を送らないクライアントや、そのファイルを持たないコンテナでは、それらのフィールドは `-` のままです。

静的アドレスの端末は、以前持っていたアドレスのリースを保持するため、カーネルの ARP テーブルがそれを正します。ルーティングモードでは `/proc/net/arp`、管理モードでは `/proc/<pid>/net/arp` で、管理モードではクライアントの LAN がコンテナ内で終わります。リースは、テーブルがそれを裏付けるか、その MAC について他のアドレスを知らない間は有効です。またテーブルは、リースを持たない端末にアドレスを与えることもあります。テーブルにあるのは何かを送信した端末だけで、古いエントリーも完了として記録するため、端末は今しがた離れたアドレスを示すことがあります。

`block <mac> [name]` は端末を `/data/local/virtualap/blocklist` に追加し、`unblock <mac>` はそれを外します。`blocked` はそれぞれについて `mac name` を出力し、名前がなければ `-` を出力します。`allow`、`disallow`、`allowed` は `allowlist` について同じことを行います。`allow-only on` は許可リストにないすべての端末を締め出し、接続中のものは切断し、リストが空の間は拒否されます。リストから最後の端末が外れるとオフになります。そうしなければ誰も参加できないからです。引数なしでは `on` か `off` を出力します。その状態はリストの隣にある `allow_only` というファイルです。リストと同じく、ホットスポットのオンかオフにかかわらず 1 コマンドずつ変わるからです。端末は 1 つのリストにだけ載り、一方に追加すると他方から外れます。`hostapd` は許可リストを先に確認し、両方に載った端末を通してしまうからです。

リストが `ap.conf` の外にあるのは、アプリが起動時に渡す設定ではなく 1 エントリーずつ編集するからです。ファイルは `hostapd` 自身の `deny_mac_file` と `accept_mac_file` で、存在するときにだけその設定に名前が書かれます。`hostapd` は開けないリストでは起動しないからです。1 行は `mac #name` です。`hostapd` は MAC の後に続くものを `atoi` で VLAN id として読み、`#` はそれを 0、つまり VLAN なしにします。動作中のホットスポットは制御ソケット経由で変更を聞きます。`DENY_ACL ADD_MAC` は端末が接続中なら切断し、許可された端末だけが参加できる状態では `ACCEPT_ACL DEL_MAC` も同様に切断します。開始時にはまずファイルを書き直し、`hostapd` が読めるか確信が持てない行はログに記録して捨てます。それぞれ約 400 台の端末を保持できます。

アプリはデバイスシートから確認なしでブロックします。すぐ隣にブロック解除があるからです。両方のリストは、ホットスポットがオフのときのために設定にもあります。MAC フィールドは 16 進数字以外を受け付けず、エンジンが拒否するもの、つまり全ゼロとグループアドレスを拒否します。どちらのリストもその MAC だけを保持します。自身の MAC を変える端末はブロックをすり抜け、許可リストから外れます。スマートフォンは既定でネットワークごとにランダムなアドレスを使うため、入力すべきは、このホットスポットについて端末の Wi-Fi 詳細に表示されるアドレスです。

## スマートフォン上

すべては `/data/local/virtualap` の下にあります：

- `bin/`：`virtualap`、`hostapd`、`dnsmasq`。スマートフォンのアーキテクチャ向けの完全に静的な musl バイナリです。`iptables` は Android 自身のものです。
- `ap.conf`：ホットスポットの設定を `KEY='value'` の行で表したもの。アプリは画面の内容が有効なときにいつでも、そして各開始の前にそれを書き、半分しか埋まっていないフォームは画面に残ります。エンジンは読むだけで、その実行に限りフラグがそれを上書きします。Wi-Fi のパスワードを保持するため、root だけが読めます。
- `blocklist`、`allowlist`、`allow_only`：ブロックされた端末と許可された端末、そしてそれらだけが参加できるかどうか。詳しくは[上記](#無線)を参照してください。初めて使うまでこれらのファイルはありません。
- `.boot_mode`：起動時にホットスポットを開始する場合に `1`。設定のトグルが書き、起動モジュールが読みます。
- `run.state`：動作中の AP が後片付けに必要とするもの、つまりゲートウェイ、上流、IPv6 のモードとインターフェース、復元する sysctl の値。`status` は「running」をこれと `hostapd` の pid ファイルから判断し、`stop` は終了する前にこれを削除します。
- `run/`：pid ファイル（`hostapd`、`dnsmasq`、モニター）、生成された `hostapd.conf` と `dnsmasq.conf`、リース、IPv6 のクライアント一覧、`hostapd` の制御ソケット、2 つの開始や停止が同時に走らないようにするロック。
- `logs/`：`ap.log`、アプリが表示したすべての行とモニターが行ったことのタイムスタンプ付きのコピーで、各開始時に切り詰められます。加えて `hostapd.log` と `dnsmasq.log`。そうしなければ両方のデーモンが失敗の理由を持ち去ってしまうからです。そして `boot-module.log`、最後の起動で起動モジュールが行ったこと。

pid ファイルに対して何かを行うのは、それが指すプロセスが期待するプログラムを実行しているときだけなので、再起動後に再利用された pid にシグナルが送られることは決してありません。アプリは初回起動時と、APK が異なるバイナリを同梱するたびに `bin/` を配備します。ビルドは各アーキテクチャのバイナリと起動モジュールのハッシュである `PAYLOAD_VERSION` をそれらの隣に書き、アプリは最後に配備したものと比較します。

バックエンドを配備すると、Droidspaces が自身のものをインストールするのと同じ方法で、起動モジュールである `/data/adb/modules/virtualap` もインストールされます。root マネージャーのないスマートフォンではこれは入らず、`.boot_mode` を書くだけの設定のトグルを読むものがなくなります。モジュールの `service.sh` は late start で実行され、`sys.boot_completed` を待ちます。`.boot_mode` がオンのときは、Wi-Fi インターフェースに現れるまで 25 秒与え、管理モードではコンテナが動作するまでさらに 25 秒与え、どちらかが間に合わなければ開始を飛ばします。ホットスポットは後から来る上流に追従するため、ネットワークは待ちません。開始は `ap.conf` を読みます。これはアプリの暗号化ストレージの外にあり、起動時の開始にロック解除は不要です。結果は root マネージャーにモジュールの説明として表示されます。開始に成功すると、アプリが動作できない最初のロック解除を待ち、`HotspotBootReceiver` にブロードキャストを送ります。これが実行中の通知を出します。

## ビルド

`hostapd` と `dnsmasq` は、`externals/` 配下の git サブモジュール（私たち自身のフォーク）から `scripts/build-static.sh` でビルドします。各アーキテクチャはそのアーキテクチャの Alpine 3.23 コンテナ内で、x86 ホスト上の QEMU の下でビルドし、`-static -no-pie` を付けるため、結果はインタープリターを持たない単体の ELF になります。`dnsmasq` のフォークは `getpwnam("root")` による特権降格を取り除いています。Android の `/etc/passwd` に root のエントリーがなく、静的 musl はそれを合成しないからです。`virtualap` は libc 以外に何もリンクせず、コンテナも必要としません。ルートの `Makefile` が Droidspaces 流にビルドし、`~/toolchains/<triplet>-cross`（または `MUSL_CROSS`）の musl-cross gcc を使って `make aarch64 armhf` を実行します。これは `buildBackend` gradle タスクが各アプリビルドの前に実行します。出力は gitignore された `backend/<arch>/` に置かれ、`prepareAssets` gradle タスクが 3 つのバイナリを APK のアセットに配置し、いずれかが欠けていると失敗します。

`src/` はレイヤーごとに 1 つのフォルダを持ち、それぞれが `src/include/<folder>/` 配下に 1 つの公開ヘッダを持ち、そのファイル同士がそれ以上のものを共有する場合はソースの隣にプライベートな `internal.h` を持ちます：`core`、`cli`、`net`（rtnetlink と `net/ipt/` の `ip_tables` エンジン）、`radio`（nl80211、制御ソケット、チャンネルポリシー）、`mode`（ルーティング、管理、IPv6、`hostapd` と `dnsmasq`）、`monitor`、`cmd` です。`make check` は `tests/` のアサートを実行し、netlink のものは使い捨てのユーザー名前空間とネットワーク名前空間の中でカーネルに対して実行するため、root もスマートフォンも不要です。スマートフォン向けにビルドしてそこで root として実行すると、実際の `ip_tables` も試されます。

CI は各アーキテクチャ向けの `hostapd` と `dnsmasq` を ARM ランナーでビルドし、`externals/` と `scripts/` のツリーでキャッシュします。続いて APK のジョブが Droidspaces の公開する musl ツールチェーンを取得し（sha256 で検証してリリース URL でキャッシュ）、警告をエラーとして `make check` と `make aarch64 armhf` を実行し、JDK 17 で APK をビルドします。`src/include/virtualap.h` の `VAP_VERSION` に一致する `v*` タグがプッシュされると、APK、`SHA256SUMS` ファイル、前のタグ以降のすべてのコミットの変更履歴を伴うリリースを公開します。タグはそれに一致し、署名鍵が存在していなければならず、そうでなければ実行は停止します。CI はフォーマッターもリンターも実行しません。

`make bump NEW=x.y.z` は `VAP_VERSION` を書き換え、Makefile、gradle、CI はすべてそこから読みます。APK の versionCode は、リリースコード（major·10000 + minor·100 + patch）に 10000 を掛け、`git rev-list --count HEAD` を足したものです。そのため各コミットの APK は前のものに上書きインストールできます。このカウントには完全な履歴が必要で、APK のジョブが `fetch-depth: 0` でチェックアウトするのはそのためです。浅いクローンは 1 を数え、`.git` のないツリーは 0 を数えます。起動モジュールの `module.prop` はリリースコードだけを取り、それは `PAYLOAD_VERSION` にハッシュ化されるからです。

## 翻訳

アプリのテキストは `Android/app/src/main/res/values/strings.xml` に、複数形はその隣の `plurals.xml` にあり、Weblate のコンポーネントは `Strings` と `Plurals` の 2 つで、Droidspaces と同じ構成です。どちらもファイル形式は Android String Resource、ファイルマスクは `Android/app/src/main/res/values-*/strings.xml` または `plurals.xml`、`values/` の基底ファイルを単一言語の基底言語ファイルと新しい翻訳のテンプレートの両方として使い、言語コードは Android 形式（`values-pt-rBR`）です。Weblate の Cleanup translation files アドオンをオンにしてください。基底ファイルから削除されたキーが翻訳に残っていると lint の `ExtraTranslation` になり、これは致命的なので、それが消えるまでリリースビルドは失敗します。翻訳がない場合は英語にフォールバックするだけです。

アプリは、設定の言語ピッカーが別を指定するまでシステムの言語に従います。ピッカーの一覧と Android 13 のアプリごとの言語一覧は 1 つのファイルです。`generateLocaleConfig` が `values-*` フォルダから `res/xml/_generated_res_locale_config.xml` を書き、`res/resources.properties` が `res/values` は英語だと述べ、`LocaleHelper` がその結果を読むため、Weblate からマージされた言語は、どれだけ翻訳が少なくても次のビルドで提示されます。選択は AppCompat を通ります。`MainActivity` が `AppCompatActivity` なのはそのためです。Android 13 以降はシステムがそれを保持し、8 から 12 では AppCompat が自身で保持してアクティビティをラップし、アプリケーションやサービスはラップしないため、そこでは通知とクイック設定タイルはシステムの言語のままです。どのバージョンでも、すでに出ている通知は次の更新で新しい言語を取ります。ログは英語のままです。それはエンジンが出力したものだからです。そのログと QR シートのパスワード用の JetBrains Mono が唯一同梱されるフォントで、翻訳されたラベルはすべてシステムのフォントなので、どんな文字体系も描画できます。
